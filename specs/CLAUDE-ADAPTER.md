# Optional Claude AgentManager

An AgentManager instance can own the pinned Claude adapter while retaining the same Hive `agent.*` tools, native method contracts, events, and input handling. The default instance continues to launch Codex. The adapter runs as its own stdio process with an instance owned Codex home, Claude configuration directory, session store, skills directory, and MCP projection. It uses the official Claude Agent SDK and a separately verified, unmodified Claude CLI executable. The selected Claude model comes from the instance settings and the adapter's `model/list` response; callers must not send Codex model IDs to this instance.

The [source only instance template](../docs/examples/services/agent-manager-claude/instance.json) starts disabled. Give the second instance a distinct service node ID, credential, `paths.data`, `paths.work`, `paths.logs`, and `settings.codexHome` under its own data root. Reuse the normal `agent-manager` component manifest. No global `codex` command replacement or shared socket is involved. The [settings schema](schemas/agent.schema.json) defines the optional `appServer.mode: "claude-adapter"` fields.

The Claude mode requires managed environment outputs and keeps skills under its isolated Claude configuration directory; omit `settings.skillsRoot`. Before launch, AgentManager applies the usual Hive and host instruction, MCP and skill documents. Its composed `AGENTS.override.md` is appended to Claude Code's system preset, including the current workspace's `AGENTS.md` when local instructions are enabled. The MCP document is projected into the adapter's SDK configuration, and Claude loads skills from the isolated `CLAUDE_CONFIG_DIR/skills` with explicit user, project and local filesystem setting sources.

## Build and check

The [lock](../services/agent-manager/claude/adapter.lock.json) and npm lock pin the vendor SDK and private transport. Build an isolated SDK directory with `node tools/package/build-claude-adapter.mjs --out <new-absolute-directory>`. This copies the transport and installs the SDK with `npm ci --ignore-scripts`; no external adapter source or patch is built. AgentManager launches its packaged Rust executable in Claude stdio mode, which owns protocol state and the SDK child.

Keep `settings.nativeVersion` at `0.142.3`, `settings.nativeExecutable` as the verified Node executable, and `settings.nativeExecutableHash` equal to the generated [catalog](native/codex-0.142.3/catalog.json) SDK bundle hash. Set `appServer.adapterRoot` to the new SDK directory and retain the Node and Claude CLI file hashes. Existing `claude-adapter` session, project, rate-limit and configuration files remain in the instance data root; the Rust store applies its existing schema migration. Rebuild the SDK directory and update its catalog hash together when upgrading.

The retained catalog exposes the supported lifecycle, transcript paging, project ownership, pending-input and model/usage discovery methods. Run `npm test -- --files tests/rust/agent-claude-adapter.rs tests/claude-adapter.test.ts` for isolated SDK/protocol checks. Production launch and reconnect checks live in [agent-native-owner.rs](../tests/rust/agent-native-owner.rs); they use an inert SDK with no account or model inference.

## Subscription boundary

Model discovery, effective configuration, permission profiles, image file reads and the Default/Plan working modes are tested native methods. A collaboration-mode request applies its model and effort to the Claude SDK; Plan mode and thread settings survive reconnects and history reads.

The launcher passes an isolated `CLAUDE_CONFIG_DIR`, a pinned official CLI path, and no inherited Anthropic API or gateway environment variables. It rejects API key, auth token, alternate base URL, Bedrock, Vertex, Foundry, and API key helper settings at startup; the adapter repeats that check against global and project Claude settings before each turn. It disables the adapter's Codex proxy route. Authentication is a later, separate operation inside the isolated Claude directory. Verify the selected account and model in the official CLI before enabling the instance. [Claude's current Agent SDK plan guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) describes subscription usage limits; [Claude Code authentication](https://code.claude.com/docs/en/authentication) documents login and API key precedence. Account level billing and live model availability cannot be established by this build.

Enablement, login, Hive registration, and a live subscription turn are separate deployment steps. Until they are performed, only isolated native protocol and SDK transport checks are verified. An unsupported model, unknown thread, billing conflict, altered adapter bundle, or missing MCP projection fails explicitly. Review the pinned SDK dependency advisories before any live enablement.
